**Procure-RL：基于 verl 的长程采购 Agent 信用分配与纠错训练**

**一、项目定位与论文依据**

建议做一个完整主项目：**面向办公电子设备采购，训练 Agent 主动发现隐藏需求、核验证据，并从错误搜索或错误判断中恢复。** 多教师 OPD 作为共用环境和评测的独立扩展，不纳入首期 6–8 周、3,000 元预算的必交付范围。

项目要验证的核心问题是：

> 终局 GRPO 无法充分区分长轨迹中有用的信息获取、无效探索和错误决策。通过可验证的过程反馈、动作级优势分配，以及学生失败状态上的专家纠错训练，能否提高任务成功率和失败恢复率？

你提供的 [GDPval，2025-10-05](https://arxiv.org/abs/2510.04374) 确实对应真实知识工作评测。这里借鉴它“围绕工作交付设计任务”的思路，将最终产物设为**包含推荐商品、约束核验和证据来源的采购建议**。GDPval 本身不是信用分配算法；终局成功率也仍然需要保留，用于判断过程训练是否真正帮助完成任务。

环境选择 **EComAgentBench 衍生环境**，训练流程借鉴你提供的 shopping-grpo-longhorizon：

`任务构建 → 专家真实执行 → 回放验收 → SFT → 在线 RL → 失败分析 → 改进与消融`

**二、业务任务与训练数据**

业务场景固定为**办公电子设备选型**，每个任务最终推荐一件商品，避免首期扩展成购物篮、订单、支付等完整电商系统。

一个示例任务：

> 为经常出差的员工选择扩展坞。预算在初始请求中，笔记本接口信息需要读取画像，双屏需求需要澄清，兼容性与供电限制需要查商品详情和评论。

Agent 需要完成需求发现、候选搜索、证据核验和最终推荐。主要失败包括：未发现隐藏限制、把相似型号混淆、忽略反证、重复搜索，以及证据不足时过早结束。

首期数据目标：

| 数据           |  目标规模 | 用途                             |
| -------------- | --------: | -------------------------------- |
| 自建训练任务   |  1,600 条 | SFT 采集、RL 与训练集失败分析    |
| 自建开发集     |    200 条 | 选择 checkpoint 和少量超参数     |
| 自建封存测试集 |    400 条 | 商品家族泛化、未见约束组合       |
| 反事实测试     |    100 对 | 改变单一约束后，决策是否相应改变 |
| 专家成功轨迹   | 约 600 条 | 冷启动 SFT                       |
| 专家修复后缀   | 约 300 条 | 纠错训练                         |

这些是采集目标，交付时报告实际数量、拒收原因和成本，不用低质量样本凑数。

数据流水线采用以下固定顺序：

1. **先处理商品事实，再生成任务。** 从结构化规格、价格和明确证据句构造约束，程序确认至少存在一个合法解，再生成请求、画像和澄清回答。允许多个商品满足条件，不能只认一个目标 ID。
2. **先划分，再改写。** 按商品家族、品牌型号及近重复簇划分数据；同一原始任务的改写和反事实样本始终留在同一 split。
3. **分阶段、多模型处理。** 默认以 `deepseek-flash` 承担任务表达和专家执行，本地 Qwen3-30B-A3B-Instruct-2507 承担独立语义核验；程序负责事实与可执行性检查。保存模型标识、日期、提示词版本和原始响应。API 别名可能升级，因此复现实验优先使用缓存的数据产物。[DeepSeek 官方接口说明](https://api-docs.deepseek.com/)
4. **程序化检查。** 检查单位换算、价格、规格一致性、可行商品存在性、证据可达性，以及初始请求是否意外泄漏隐藏需求。
5. **去重与人工审核。** 使用规范化文本哈希、MinHash、商品家族关联和语义近重复检索；抽检至少 200 条，所有模型分歧样本进入人工审核队列。
6. **真实执行验收。** 专家必须调用环境工具。只接受回放结果一致、最终满足硬约束的成功轨迹；失败轨迹保留，用于错误分类。
7. **构造反事实。** 修改预算、接口要求或使用偏好等单一条件，重新计算合法解。仅改写措辞的样本属于表达增强，单独记录。

保留官方 662 个任务作为外部测试，不用于训练、选 checkpoint 或修改奖励；其目标商品及近重复家族不进入训练任务和训练检索子库。官方测试沿用官方评分口径，与自建确定性测试分开报告。这只能控制项目新增训练造成的污染，不能证明基座预训练从未接触过相关商品数据。

环境保留英文任务，项目报告和面试材料使用中文。商品数据库固定版本与哈希；训练阶段采用只读、按 split 过滤的检索视图。[官方数据构建入口](https://github.com/Morizeyao/EComAgentBench_/blob/main/src/generation/pipeline.py)

**三、算法与 verl 实现**

主流程分为三个阶段：

`成功轨迹 SFT → 终局 GRPO baseline → 动作级过程信用分配 → 失败前缀纠错 SFT`

**1. 先建立可信 baseline**

学生模型固定为 [Qwen3-4B-Instruct-2507](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507)，采用 LoRA。它支持工具使用且只有非 thinking 模式，便于控制轨迹长度和监督范围。

SFT 只监督 assistant 生成的动作，屏蔽用户、工具返回和历史错误前缀。RL baseline 使用确定性终局奖励：

- 最终推荐满足全部硬约束：1。
- 推荐错误、未完成或超过预算：0。

同时记录分项约束满足率，但不把它混入 baseline 奖励。

**2. 引入可验证的过程反馈**

每次动作执行后，根据实际 observation 记录事件：

- 首次揭示任务相关的隐藏需求。
- 首次获取可支持或排除候选的必要证据。
- 无效工具调用。
- 重复调用且没有取得新信息。

正反馈按有限 rubric 条目分配：隐藏需求占 40%，证据获取占 60%，每条轨迹正奖励预算不超过 1。无效调用初始扣 0.05，重复无进展调用扣 0.02。

重复读取同一事实不再奖励；模型自行声称“已核验”不算完成；不额外奖励“修复自己刚制造的错误”。这些反馈衡量可观测进展，最终成功仍由独立终局验证器决定。

**3. 真正改到动作级优势**

标准 verl GRPO 会先把 token rewards 求和，再给整条回答广播同一优势。因此仅增加过程分数，仍然没有完成时间上的信用分配。[固定版本优势源码](https://github.com/verl-project/verl/blob/v0.8.0/verl/trainer/ppo/core_algos.py)

本项目采用 **TRCA 启发的 rubric 反馈，加动作级 return-to-go 和 leave-one-out baseline**，明确作为项目改造：

\[
H_{i,t}=\sum_{k=t}^{T_i}0.95^{k-t}c_{i,k}
\]

\[
D_{i,t}=H_{i,t}-\frac{1}{G-1}\sum_{j\ne i}H_{j,t},\qquad G=4
\]

其中，其他轨迹已经结束的位置视为吸收状态，过程回报为零。这个比较用于降低方差，不声称同一序号的动作具有相同语义。

对 \(D\) 按有效动作的 RMS 缩放，分母下限为 0.1，裁剪至 \([-3,3]\)，再与终局优势合并：

\[
A_{i,t}=A_i^{terminal\text{-}GRPO}+0.2A_{i,t}^{process}
\]

过程回报只包含过程反馈，避免重复计入终局奖励。过程权重仅在开发集小规模比较 \(0.1/0.2/0.3\)，之后冻结。

优势广播到**当前动作生成的 token**，工具 observation 不参与损失。折扣按环境动作计算，不能沿 JSON token 逐个折扣。

**4. 专家知识通过失败状态进入训练**

先用 baseline 在训练任务上收集失败轨迹，按错误类型定位可恢复前缀。教师从相同快照继续操作，只看到当时已经可见的信息；私有答案仅用于验收。

保留成功修复的后缀，进行 action-only SFT。错误历史作为上下文，其 token 不参与损失。终局推荐已经结束的任务，在离线采集时回到结束前的状态，不给测试 Agent 增加无限撤销能力。

这一部分称为**学生失败状态上的专家纠错蒸馏**。它属于轨迹监督，不称为 token-level OPD。

**5. 工程接口**

使用 **[Modern veRL] `verl==0.8.0`**，固定 `main_ppo` 入口和依赖锁文件，避免混用不同版本数据流。

新增三个项目接口：

- 环境：`reset / step / snapshot / restore`；快照包含澄清状态、事件历史、剩余步数和随机状态。
- 轨迹：记录 `turn_spans、step_rewards、verifier_events、policy_version`。
- 优势计算：通过 `extra_fields → DataProto.non_tensor_batch` 传递步骤信息，为自定义 estimator 增加明确的 trainer 参数透传。

仅注册 estimator 不够，默认 trainer 不会自动把全部步骤元数据传给它。[AgentLoop 源码](https://github.com/verl-project/verl/blob/v0.8.0/verl/experimental/agent_loop/agent_loop.py)、[trainer 源码](https://github.com/verl-project/verl/blob/v0.8.0/verl/trainer/ppo/ray_trainer.py)

主任务最多 40 次工具调用，压力测试提高至 80 次；官方外测保留原协议。报告实际成功轨迹长度、必要证据数和隐藏约束数，不能用允许的最大步数代替长程难度。

**四、实验、归因与验收**

实验矩阵围绕“收益究竟来自哪里”组织：

| 编号 | 实验                               | 要回答的问题                       |
| ---- | ---------------------------------- | ---------------------------------- |
| B0   | 原始模型、成功轨迹 SFT             | 冷启动贡献多少？                   |
| B1   | SFT + 终局 GRPO                    | 强化学习 baseline 是什么水平？     |
| B2   | 终局优势 + 汇总后广播的过程优势    | 单纯增加过程信息是否有效？         |
| B3   | 终局优势 + 动作级过程优势          | 反馈分配到不同动作是否进一步有效？ |
| B4   | 将 B3 的过程优势在同轨迹动作间打乱 | 正确的反馈位置是否重要？           |
| B5   | B3 + 失败前缀纠错 SFT              | 训练恢复行为是否有效？             |
| B6   | B3 + 等量普通成功轨迹 SFT          | B5 的提升是否只是更多监督训练？    |

B2/B3 使用相同过程事件、权重和缩放规则；B5/B6 匹配监督 token 数与更新次数。所有 RL 组记录环境交互量、生成 token、更新 token 和 GPU 时间，展示成功率随交互预算变化的曲线。

主要指标：

- 全部硬约束满足的任务成功率。
- 按 query、persona、clarification 来源拆分的约束满足率。
- 固定失败前缀上的恢复成功率。
- 反事实约束改变后的正确决策率。
- 每个成功任务的工具调用数、生成 token 和训练成本。
- 证据缺失、重复循环、过早推荐、上下文截断等错误占比。

在封存测试集上做任务级配对比较与 bootstrap 区间；反事实兄弟样本按原始任务成组抽样。B1、B3、B5 至少运行两个训练随机种子，报告单次结果和均值，不把任务抽样区间冒充训练种子不确定性。

另外，从开发集固定抽取少量决策状态，用相同后续预算进行原动作与替代动作的分支续跑，检查过程评分是否与后续成功变化相关。这是有限回放审计，不宣称识别出真实因果信用。

必须通过的实现测试：

- 同一快照和动作产生相同 observation；并发任务不串状态。
- 工具 observation 变长，不改变按动作计算的回报。
- 不同任务不会混入同一个 leave-one-out 组。
- 用户、工具和 padding token 无训练损失。
- 重复查证、关键词堆砌、错误后再修复不能刷取正奖励。
- 非法动作、提前终止、超长截断均有明确日志和计分。
- 程序验证器与人工核验一致；修复评分错误后，相关模型统一重评。

预期目标是观察到 B3 对 B1、B5 对 B6 的稳定改善；不预先承诺提升百分点。没有提升时，依据错误分布和消融结果解释原因，保留负结果。

**独立扩展：token 级多教师 OPD**

主项目完成后，复用环境与评测，分别训练“需求发现/搜索”和“约束核验/纠错”两个同 tokenizer 的专家。先在开发集证实二者具有互补能力，再比较：

`最佳单教师 → 两教师均匀混合 → token 级 Entropy 路由`

学生生成当前轨迹，两位教师对同一批学生 token 顺序强制打分：

\[
A_t^{OPD}
=\sum_j w_{j,t}
\big[\log\pi_{T_j}(y_t\mid h_t)-\log\pi_{old}(y_t\mid h_t)\big]
\]

教师逐 token 权重必须真正变化；熵使用完整分布计算并分块处理显存。每个更新周期重新生成学生轨迹，缓存绑定策略版本和轨迹哈希。
