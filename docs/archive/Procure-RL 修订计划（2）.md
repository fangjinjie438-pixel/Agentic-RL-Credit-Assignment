**Procure-RL 修订计划：学校 A6000 优先、verl 0.6.1、分阶段实现与可接续文档**

**一、结论与技术选型**

**学校服务器可以承担本项目的大部分工作，包括正式训练；4B 保留为主实验模型。** 推荐路线为：

`本机完成 CPU 开发 → 学校单卡小模型冒烟 → 学校双卡 4B 实验 → 按需使用第三卡或 AutoDL → 有依据时扩展 8B`

小模型能降低调试成本，学校算力能减少租卡支出，但目前没有吞吐实测，不能承诺具体节省比例。小模型用于验证代码、数据流和训练链路，其 checkpoint 不直接迁移成大模型 checkpoint。

当前已存在的[项目计划文档](</D:/Agentic-RL/Procure-RL：基于 verl 的长程采购 Agent 信用分配与纠错训练.md>)作为计划唯一来源，实施阶段更新该文件，不另建相互冲突的计划副本。**本轮处于计划模式，尚未修改文档或创建代码。**

**框架版本采用 verl 0.6.1，先通过学校服务器预检再锁定环境。**

`nvidia-smi` 显示的 CUDA 12.6 是驱动支持信息，不等于实际安装的 Toolkit 或 PyTorch 使用的 CUDA runtime。CUDA 12.x 存在小版本兼容，但 PTX/JIT 和新驱动特性有边界，因此不能直接判定 verl 0.8.0 必然不能运行。[NVIDIA 兼容性说明](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html)

本项目选择 0.6.1，是因为找到了一条更明确的 cu126 配套路径：

| 组件         | 首选待验证版本                   |
| ------------ | -------------------------------- |
| Python       | 3.11                             |
| verl         | v0.6.1，记录具体 commit          |
| PyTorch      | 2.7.1，cu126                     |
| vLLM         | 0.10.0，官方 cu126 wheel         |
| Transformers | 4.53.2                           |
| 训练方式     | BF16、LoRA、FSDP2                |
| 多轮训练入口 | `main_ppo`、AgentLoop、DataProto |

vLLM 0.10.0 的官方依赖固定 PyTorch 2.7.1，且确实发布了 cu126 wheel。这是有源码依据的候选组合，完整依赖锁仍需安装检查和 GPU 验证后生成。[vLLM 依赖](https://github.com/vllm-project/vllm/blob/v0.10.0/requirements/cuda.txt)、[官方安装包](https://github.com/vllm-project/vllm/releases/expanded_assets/v0.10.0)

不使用裸 v0.6.0：其多轮异步路径缺少本项目需要的完整 LoRA 选择与同步支持，0.6.1 已有相关实现。不能用“单轮 LoRA 可运行”证明“多轮训练时 rollout 使用了最新 adapter”。[v0.6.0 源码](https://github.com/verl-project/verl/blob/v0.6.0/verl/workers/rollout/vllm_rollout/vllm_async_server.py)、[v0.6.1 源码](https://github.com/verl-project/verl/blob/v0.6.1/verl/workers/rollout/vllm_rollout/vllm_async_server.py)

安装使用用户独立环境，不修改学校系统驱动。若候选环境失败，保留报错并定位具体依赖或接口，不自动升级到另一套框架。

**模型采用三级策略。**

| 用途     | 模型                      | 要验证的内容                                 |
| -------- | ------------------------- | -------------------------------------------- |
| 工程冒烟 | Qwen3-0.6B，关闭 thinking | 多轮交互、奖励、反向传播、权重同步、保存恢复 |
| 主实验   | Qwen3-4B-Instruct-2507    | 完整 baseline、过程信用分配、纠错与消融      |
| 条件扩展 | Qwen3-8B，关闭 thinking   | 能力瓶颈诊断或第二模型迁移验证               |

如果 0.6B 连合法动作都难以生成，改用 1.7B 完成动态链路验证，不在小模型上投入正式算法实验。

**4B 不应仅因参数量较小而被排除。** 官方模型卡已有工具调用和零售任务能力评测，但这些不能代替本项目测试。[4B 模型卡](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507)

Qwen3 对应的下一档是 8B；换成 Qwen2.5-7B 还同时改变模型代际。4B-Instruct-2507 与 Qwen3-8B 的后训练版本也不同，因此结果应称“第二模型验证”，不能当成严格的参数量消融。[Qwen3 型号与说明](https://qwenlm.github.io/blog/qwen3/)

**二、学校资源分配与升模规则**

学校资源按需要排队、通常能获得两卡、可能获得三卡来设计。

| 资源                | 默认工作                                           |
| ------------------- | -------------------------------------------------- |
| 本机 CPU            | 环境逻辑、数据检查、优势计算测试、配置、文档       |
| 学校单卡 A6000      | 小模型冒烟、单卡推理、SFT 预检、4B 显存测试        |
| 学校同交换机双卡    | 4B 主训练、baseline、信用分配和主要消融            |
| 学校第三卡          | 独立评测，或通过吞吐测试后加入 FSDP                |
| 跨 host bridge 的卡 | 分配到时用于独立推理、数据复核或 checkpoint 评测   |
| AutoDL              | 学校资源不足、目标上下文无法承载或需要赶进度时补充 |

PIX 表示 PCIe switch 路径，不代表 NVLink，也不能单独证明 P2P 实际正常。先检查拓扑，再测试实际传输和 NCCL；第四卡不默认加入同步训练。[NVIDIA 拓扑定义](https://docs.nvidia.com/deploy/nvidia-smi/index.html)

配置原则：

- 默认训练使用两卡 FSDP2，rollout `TP=1`，序列并行先设为 1。
- 三卡训练采用 FSDP 与单卡 rollout 副本，不设置 `TP=3`。
- 正式初始 global prompt batch 为 6，每题 4 条 rollout，共 24 条，兼容双卡和三卡分配。
- LoRA rank 32、alpha 64，训练 microbatch 1，开启 gradient checkpointing。
- 单卡初始 rollout 并发 1；根据显存与吞吐再增加。
- 冒烟总上下文 2K–4K；正式主实验目标 12K。正式模型之间使用相同上下文与任务预算。
- 多卡总显存不等于一张大显存卡；`TP=1` 时，每张卡仍需容纳完整推理权重和该卡 KV cache。

硬件预检记录 GPU 型号、UUID、空闲显存、拓扑、P2P、CPU/内存、磁盘、共享内存、驱动、Toolkit、Torch CUDA、NCCL 和包版本。只在获分配的 GPU 上进行实际计算测试。

**是否升级 8B，由开发集决定。**

冻结开发集中的 128 个分层任务，每题生成 4 条轨迹，检查：

1. SFT 后工具调用格式是否合法；目标合法率至少 98%。达不到时先修模板、数据与协议。
2. 分别记录全失败、全成功和混合结果的 rollout 组比例。
3. 若 4B 已有可学习的成功轨迹和混合组，继续完成主实验。
4. 若成功率低于 5%、全失败组超过 80%，先排除上下文截断、奖励错误、数据质量和 LoRA 同步问题，再进行 8B pilot。
5. 仅当 8B 使用相同任务、信息与训练数据后取得明确改善，且吞吐允许完成主要对照，才考虑更换主模型。

上述阈值是工程诊断默认值，不是容量定律。测试集不参与升模选择。

正式实验优先在学校完成；3,000 元仍是外部开销上限，其中 API 500 元、存储及预留 300 元、AutoDL 备用额度 2,200 元，不要求全部花完。学校 GPU 小时仍单独记录。

**三、项目方法与实验协议**

项目仍聚焦**办公电子设备采购中的隐藏需求发现、证据核验与失败恢复**，以 EComAgentBench 衍生环境为主。最终输出推荐商品及可追溯的约束证据。

研究依据保留：TRCA 的状态转移反馈、SWE-MILE 的进展与回退信用、LoongReflect 的纠错监督，以及执行回放审计。实现为项目适配，不宣称完整复现这些论文。[TRCA](https://arxiv.org/abs/2608.16156)、[SWE-MILE](https://arxiv.org/abs/2609.32631)、[LoongReflect](https://arxiv.org/abs/2608.11967)、[信用审计](https://arxiv.org/abs/2608.19760)

数据规模目标：

- 训练任务 1,600 条、开发集 200 条、封存测试集 400 条。
- 反事实测试 100 对。
- 专家成功轨迹约 600 条，失败前缀修复后缀约 300 条。
- 官方 662 个任务保留为外部测试，单独采用官方评分口径。

数据处理按“商品事实与可行解 → 商品家族划分 → 多模型生成和复核 → 程序检查 → 去重 → 人工抽检 → 真实执行验收”进行。改写和反事实兄弟样本不能跨 split；训练检索子库排除测试商品家族。每条数据保存来源、版本、验收与拒收记录。

离线教师采用 API，独立语义复核优先使用学校单卡可运行的 8B 模型，程序验证器和人工抽检承担最终事实核验，不因名称叫“教师”就默认模型正确。

训练与算法固定为：

1. 成功轨迹 action-only SFT，导出合并权重作为 RL 起点。
2. 终局 GRPO：全部硬约束满足奖励 1，否则 0。
3. 过程反馈：首次揭示隐藏需求、首次获取必要证据，无效调用和重复无进展调用。
4. 动作级过程回报与 leave-one-out baseline。
5. 从学生训练集失败状态采集专家修复后缀，进行纠错 SFT。

过程正奖励总预算不超过 1，其中隐藏需求占 40%、证据占 60%；无效调用扣 0.05，重复无进展调用扣 0.02。重复事实不重复奖励，不设置“自行制造错误再修复”的独立奖金。

\[
H_{i,t}=\sum_{k=t}^{T_i}0.95^{k-t}c_{i,k},\qquad
D_{i,t}=H_{i,t}-\frac{1}{G-1}\sum_{j\ne i}H_{j,t}
\]

其他轨迹已结束的位置，过程回报为零。对有效动作的 \(D\) 做 RMS 缩放，分母下限 0.1，裁剪至 \([-3,3]\)：

\[
A_{i,t}=A_i^{terminal\text{-}GRPO}+0.2A_{i,t}^{process}
\]

折扣按环境动作计算。过程项不重复计入终局奖励；优势只分配到对应动作生成的 token，工具和用户 token 不参与损失。过程权重仅在开发集比较 \(0.1/0.2/0.3\)，之后冻结。

verl 适配使用 v0.6.1 的 AgentLoop 与 DataProto 路径：

- 环境提供 `reset / step / snapshot / restore`。
- 轨迹保存步骤 token 范围、过程奖励、验证事件、策略版本。
- 通过 `extra_fields` 传递步骤元数据。
- 为自定义优势计算增加显式 trainer 参数透传。
- 改动集中在项目适配层；必须修改上游时，保存带版本校验的补丁与说明。[v0.6.1 AgentLoop](https://github.com/verl-project/verl/blob/v0.6.1/verl/experimental/agent_loop/agent_loop.py)、[trainer](https://github.com/verl-project/verl/blob/v0.6.1/verl/trainer/ppo/ray_trainer.py)

实验编号保持稳定：

| 编号 | 实验                            |
| ---- | ------------------------------- |
| B0   | 原始模型与成功轨迹 SFT          |
| B1   | SFT + 终局 GRPO                 |
| B2   | 终局优势 + 汇总后广播的过程优势 |
| B3   | 终局优势 + 动作级过程优势       |
| B4   | B3 的过程优势在同轨迹动作间打乱 |
| B5   | B3 + 失败前缀纠错 SFT           |
| B6   | B3 + 等量普通成功轨迹 SFT       |

B1/B3/B5 优先两个训练种子；B2/B4/B6 先完成一个种子，若相关机制作为最终主要结论，再补第二个。B5/B6 从同一个 B3 checkpoint 成对分支，匹配监督 token 和更新次数。

主指标包括任务成功率、隐藏需求满足率、固定失败前缀恢复率、反事实正确率、工具调用与 token 成本。同时报告各训练种子和按任务配对的 bootstrap 区间。

**四、分阶段代码实现与验收**

按阶段顺序实现；每阶段包含可运行代码、必要测试、操作 README 和进度更新。阶段完成不额外触发一次授权确认；远端验证未完成时，继续能够独立完成的本地模块。

| 阶段                       | 代码与功能                                                   | 验收要求                                                     |
| -------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **S0：工程与运行环境**     | Python 包结构、配置加载、依赖候选与锁定流程、硬件 doctor、日志与运行清单、文档骨架 | 本机 CPU 检查通过；远端输出硬件报告；环境安装与验证状态分别记录 |
| **S1：环境和验证器**       | ECom 适配器、只读商品访问、任务会话、工具协议、快照回放、终局与过程验证器 | 小型固定数据可在 CPU 上完整执行；快照一致、会话隔离、约束判定正确 |
| **S2：数据流水线**         | 任务构建、商品家族划分、去重、反事实生成、教师采集、轨迹回放过滤、数据清单 | 先交付小规模端到端样例；通过泄漏与可行性检查后扩到目标规模   |
| **S3：SFT 与真实多轮推理** | 动作监督数据转换、HF/PEFT SFT、合并导出、推理评测、verl AgentLoop | 0.6B/1.7B 真实多轮运行；屏蔽正确；LoRA 确实改变推理概率；保存恢复有效 |
| **S4：终局 RL baseline**   | 0.6.1 训练入口、终局奖励、单卡/双卡配置、checkpoint 和诊断指标 | 连续至少 5 次真实更新；验证 actor→rollout 同步；4B 完成 pilot 与开发集诊断 |
| **S5：动作级信用分配**     | 过程事件、动作回报、leave-one-out 优势、B2/B3/B4 开关及分析  | 数值与掩码测试通过；同信号、同预算比较；重复操作不能刷奖励   |
| **S6：纠错闭环**           | 失败分类、可恢复前缀定位、专家后缀采集、后缀监督、B5/B6 成对训练 | 修复轨迹可回放；历史错误不被当成正确输出训练；数据量与更新预算匹配 |
| **S7：正式评测与交付**     | 封存测试、外部评测、配对统计、成本汇总、案例报告、复现入口   | 输出实验表、学习曲线、至少 10 组失败/修复案例及完整运行清单  |
| **S8：可选 OPD 扩展**      | 双专家互补验证、学生轨迹强制打分、均匀混合与 token 路由      | 独立于主项目验收，不占首期必交付范围                         |

代码组织按功能划分为运行环境、交互环境、数据、轨迹、SFT、verl 适配、奖励、优势、纠错和评测模块。模块之间使用显式数据结构，不通过读取日志字符串传递训练状态。

本机安装 CPU 开发依赖，Linux GPU 依赖单独管理。环境和算法测试不依赖下载大模型或连接教师 API；真实 GPU 集成测试另设标记，不能被 CPU 测试结果替代。

检查点恢复区分两种情况：

- 相同框架、模型、world size 和配置：验证优化器、调度器、随机状态及数据位置的恢复。
- 跨卡数或不同训练环境：默认导出可移植模型权重，作为新 run 启动，不直接假定分片优化器可以无缝恢复。

周期保持 6–8 周：S0–S1 在第 1 周，S2 在第 2 周，S3–S4 在第 3 周，S5 在第 4–5 周，S6 在第 6 周，S7 在第 7–8 周。排队等待期间推进 CPU 模块、数据审核和文档。

- 操作命令必须注明实际验证状态；未经远端运行的命令不能标为已验证。

**根目录 AGENTS.md 固定包含以下规则：**

1. 开始工作先阅读 `AGENTS.md → 项目计划 → PROGRESS.md → 当前阶段操作文档`。
2. 以锁定的 verl 0.6.1 源码为准；引用其他版本时明确标注，禁止混用 API。
3. 按阶段实现、测试和记录；不得将占位实现或 mock 测试标为真实集成完成。
4. 保持训练/开发/测试边界，不使用测试结果调整奖励或选择模型。
5. 任何代码改动同步维护文件说明、README 和进度记录。
6. GPU 任务只使用分配给项目的设备；不改系统驱动或其他用户环境。
7. 训练结果必须有配置、数据版本、模型版本、命令和日志证据。
8. 缺少远端资源时明确记录未验证内容，继续推进不依赖该资源的工作。
9. 每次结束工作前更新交接记录，写明下一步具体动作。
10. 真正实现的时候需要一个阶段一个阶段地实现，实现完一个阶段就停止
